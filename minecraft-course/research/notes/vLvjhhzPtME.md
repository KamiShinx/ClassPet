# Blockbench Tutorial for Beginners: How to Make Minecraft Models (2026) (CountFrogg, 8.0 min)

**What it is:** Part 1 of a 3-part beginner series — a screen-recorded, step-by-step walkthrough modelling a simple low-poly "kiwi" character in Blockbench, covering the absolute basics of the tool (navigation, add cube, move/resize/rotate/pivot, duplicate, mirror).
**Substance:** substantive as a pure how-to, but narrow: it teaches Blockbench's core modelling controls competently and at a genuinely beginner-appropriate pace, but stops before texturing (part 2) and never touches Minecraft-specific export/rigging concerns — and, importantly, the model it builds is explicitly NOT in a Minecraft-usable format (see caveats).

## Ideas, in the video's order
- [0:00:32] Blockbench is cross-platform (desktop app, web app, and mobile/tablet) and the interface/controls are stated to be identical across versions.
- [0:01:03]-[0:01:36] First real decision point: Blockbench asks you to choose a model FORMAT when creating a new file. The video explicitly selects **"Generic Model"** from a list that also includes Java Block/Item, Bedrock Entity, Bedrock Block, and Modded Entity (see frame [0:01:12]-[0:01:20] and caveats below) — chosen because the tutorial says "everything else isn't important right now."
- [0:01:36] Basic UI layout taught: left = texture/UV space, right = element (outliner/transform) space, center = 3D workspace; panels are user-resizable/moveable.
- [0:02:10] Core navigation controls taught explicitly: scroll wheel = zoom, left-click-drag = rotate view, right-click-drag = pan — same behavior on trackpad.
- [0:02:41] First modelling action: "Add Cube" from the Add Element dropdown — the video is explicit that a cube is the base primitive for everything.
- [0:02:41]-[0:03:45] Core transform tools taught with keyboard shortcuts: Move (V, drag colored arrows along X/Y/Z), Resize (S, drag colored corner/face handles) — and a specific trick: holding Alt while resizing extends the cube symmetrically in both directions from center at once.
- [0:03:45]-[0:04:18] Build-order logic modelled live: start with one big cube for the body, then move it upward (V) to leave room underneath for legs — building "the biggest, simplest shape first, then add smaller details."
- [0:04:18]-[0:04:51] Beak added as a second cube, sized and placed by eye, described as functionally necessary ("it'll look absolutely horrific without one") as well as thematically appropriate for a kiwi.
- [0:04:51]-[0:05:26] Legs/feet built as pairs of small flat cubes; explicit terminology: **"zero pixels thick"** used loosely to mean "squashed flat" (resize one axis to ~0), not a literal pixel measurement.
- [0:05:26] Efficiency technique: select multiple elements at once with Ctrl+left-click-drag, then Ctrl+D to duplicate a matched pair (used to mirror the first leg/foot into the second) instead of manually re-building and re-sizing each part.
- [0:06:31]-[0:07:05] Two more tools taught: **Rotate** (R, drag colored curved handles) and **Pivot** (repositions the point an element rotates around) — demonstrated by adding whiskers next to the beak, discovering the default pivot point makes rotation look wrong, then manually moving the pivot to the beak's center to fix it.
- [0:07:05] Final trick: duplicate the whiskers, then use the "Flip X" button to mirror them automatically into a symmetrical pair, rather than manually rotating/positioning a second copy.
- [0:07:37] Explicitly scoped as part 1 of 3 — texturing is deferred to "the next part" (the batch's other CountFrogg video).

## For our class (11-13, Minecraft mod, Gemini writes the code)
### Realistic timeline for an 11-13-year-old with no 3D experience
This single 8-minute video, followed carefully, teaches enough (add cube, move, resize, rotate, pivot, duplicate, mirror) to build a simple multi-part low-poly creature in roughly **45-75 minutes of hands-on practice** for an 11-13-year-old with no 3D experience — the tool's core interactions are genuinely few and the video's pacing (one tool at a time, immediately applied) is age-appropriate. Realistically, expect: session 1 (a full 65-70 min class) to comfortably cover navigation + cube add/move/resize + building one simple 2-4-cube creature; rotate/pivot/mirror (the whiskers section) is the trickiest conceptual jump in the video (pivot point confusion is real and the video itself has to backtrack to fix it) and may need a second short session or one-on-one help for several of the 8 kids. A simple original mob (not copying the kiwi) is realistic as homework/second-session output once the tool basics land.

### Traps flagged for the class
- **Format mismatch (the big one — see caveats)**: this tutorial builds in "Generic Model" format, which its own dialog says explicitly is NOT loadable into Minecraft. For the class's actual NeoForge-mod goal, kids must instead pick **"Modded Entity"** (the Java-mod-facing format Blockbench lists) — or whatever format actually round-trips into a NeoForge Java mob/item. This tutorial does not show that path at all, so a teacher must substitute the correct format choice at the very first "New Model" dialog and cannot otherwise follow this video verbatim.
- **Pixel density / UV mismatch**: the project's UV Size defaults to 16x16 per the dialog shown, matching Minecraft's real per-face texture convention — good — but the video never explains what happens if a model's cube proportions don't map cleanly onto that 16x16 grid (e.g., an oddly-sized cube face producing a stretched or misaligned texture later). This is a real trap CountFrogg's own texturing video (companion in this batch) is more likely to address.
- **Pivot-point confusion**: the video's own mid-tutorial backtrack (whiskers rotating around the wrong point until the pivot is manually moved) is a realistic preview of where an 11-13-year-old will get stuck — worth pre-empting with a short "what is a pivot" mini-explanation before kids reach that step, rather than letting them discover the bug themselves.
- **Bedrock vs Java is NOT addressed at all**: the format-selection screen shows both Bedrock Entity/Bedrock Block and Java Block/Item/Modded Entity as options, but the video never explains the difference or why it matters. Given CONTEXT.md's locked stack (Java + NeoForge), the class needs a short, explicit rule stated by the teacher, not inferred from this video: **always pick the Java/Modded Entity path, never Bedrock.**

### Open questions this video does not answer (flag, don't guess)
- What exact Blockbench format/export setting produces a model usable by a NeoForge Java mod (this video only shows "Generic Model," which is explicitly incompatible, and briefly flashes "Modded Entity" as a menu option without explaining it).
- Whether "Modded Entity" format requires any additional Java-side rigging/bone-naming convention to work with NeoForge's entity renderer.
- How the exported model file (format, filename convention, folder location) actually gets referenced from the Gemini-written Java code — entirely outside this video's scope.
These should be tested directly (open Blockbench, try Modded Entity format, attempt a real NeoForge import) rather than assumed, before building a class lesson plan around it.

## Honest caveats
The most important caveat is structural, not a matter of opinion: **this beginner tutorial's own on-screen dialog states the chosen format cannot be loaded into Minecraft**, and the narration never flags or corrects this. A teacher following this video literally with the class would produce kiwi models that don't import into the actual mod project — this must be caught and corrected (use "Modded Entity" or the correct Java-compatible format) before running this as a class activity, not discovered after. Everything else taught (cube-based modelling, move/resize/rotate/pivot/duplicate/mirror) is format-agnostic tool literacy and remains valid regardless of which format is ultimately chosen. The video is a straightforward tutorial with no design theory — it doesn't address WHY a shape choice is good (no silhouette/palette discussion, unlike the two Mojang videos in this batch), so it should be paired with the Mojang design-principles videos, not treated as a full design lesson on its own.

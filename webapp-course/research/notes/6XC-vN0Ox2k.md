# Build a Web App with Gemini AI + Apps Script (No Coding Needed) (NeoSimpleLab, 14.6 min)

**What it is:** a promo/tutorial for the creator's own free template project ("AI Architect & Designer") that wraps the Gemini API in a wizard UI to generate Apps Script web apps. 2025/2026-era (mentions Gemini API, Google AI Studio keys). Half demo of 3 finished apps, half real how-to.
**Substance:** mixed: the demoed apps are shallow (no auth security, plaintext passwords) but the **workflow of how Gemini's output actually gets into the Apps Script editor is shown concretely and is the most useful thing in this video for the brief**.

## Ideas, in the video's order
- [0:01:06] Demo 1: an AI-generated "mini supermarket" app that seeds its own Sheet with sample data on first run if the Sheet is empty (a self-bootstrapping backend pattern).
- [0:02:13–02:46] Places a real order in the demo app; confirms the Apps Script backend actually created new Sheet tabs (`orders`, `order items`) and wrote rows — i.e., verifies the AI-written backend works, doesn't just claim to.
- [0:03:19–03:52] Demo 2: a pizza-ordering app with signup/login; explicitly flags that user records (including password) are stored in the Sheet in the open and says **"in a real-world application, you should encrypt passwords and implement proper authentication"** — a real, stated security caveat from the video itself, not just my inference.
- [0:04:24] Demo 3: a two-account chat app, used only to show that multiple users writing at once doesn't break anything (implicit concurrency check, not explained).
- [0:04:57] **The actual workflow, part 1 — getting the tool**: make a copy of the creator's Apps Script project into your own Drive (right-click > Make a copy), open the copy, deploy it once as a plain empty web app (Extensions > Apps Script > Deploy > New deployment > Web app > Anyone/Anyone with Google account > Deploy > authorize).
- [0:05:30] **Workflow part 2 — bringing your own AI key**: the deployed empty app has a key icon; click it, paste a **free Gemini API key you get yourself from Google AI Studio**, save. This is a different pattern than "chat with Gemini and copy code" — the key lets the *app itself* call the Gemini API server-side/client-side to write its own code.
- [0:06:03–08:47] **Workflow part 3 — describing the app**: a general one-line description, then three structured "layers" you fill in: (1) Business Logic & Behavior — the workflows, in plain language; (2) UI System Library — screens/components (top bar, sidebar, forms, dashboard); (3) Technical Stack — pick frontend (HTML/CSS), image source (Unsplash), backend (Apps Script, fixed), and database (Sheets, fixed). This is essentially a structured prompt template broken into fields instead of one giant free-text prompt.
- [0:09:21] Click "Create Web App" → the tool calls Gemini and prints two file blocks directly on the page: the frontend HTML and the `Code.gs` backend — visibly split into the two file types Apps Script expects.
- [0:09:54] **Workflow part 4 — how code actually gets into the editor: manual copy-paste**, file by file. Open the Apps Script project, paste the HTML into `index.html`, paste the generated code into `Code.gs`, save both, then Deploy > New deployment again to get a URL.
- [0:11:32] **Workflow part 5 — iterating on the UI without breaking the backend**: open a *separate* Gemini chat (gemini.google.com) in Canvas mode (explicitly chosen because Canvas "is designed to work directly with large code blocks"); paste the *entire* `index.html` file into Canvas; prompt a change ("add a background image and analytics charts"); Gemini rewrites the whole file.
- [0:12:05] **Named anti-breakage technique, stated on camera**: the presenter says the HTML template already has "special instructions inside the file" acting as "guard conditions" telling the AI not to change how the frontend talks to the Apps Script backend — i.e., inline comments in the prompt-adjacent code are used deliberately to stop Gemini from regressing a working integration when asked for an unrelated UI change.
- [0:13:13] Copy the *entire* updated file back out of Gemini Canvas, paste over `index.html` in Apps Script, save, redeploy, and re-test that the "add product" call still reaches the Sheet — confirming the guard-comment technique worked.

## For our class (14-15, Gemini writes the code, Apps Script + Sheets)
### Backend concepts it shows or explains
Self-seeding demo data when a Sheet is empty; splitting a generated app into exactly two files (frontend HTML, backend `.gs`) that Apps Script expects; a deployed web app calling an external AI API using a user-supplied key (relevant if the class ever wants an "AI feature" inside a kid's own app, distinct from *using* Gemini to author the code); and the core idea that **frontend changes and backend/API-contract stability are separate concerns** that need to be explicitly protected.

### Becomes something kids do (activity, mini-project, milestone), concrete enough to run next week
Two separate, directly reusable habits, not a project to copy wholesale (the demoed apps — supermarket/pizza/chat — are too broad for a first build):
1. **Structured prompting**: instead of one long ask, have kids write three short paragraphs before asking Gemini for a first version — what it does (business logic), what's on screen (UI), and what it's built on (Apps Script + Sheets, always fixed for us) — mirroring this video's 3-layer form. Backend concept taught: **separating "what happens" (server logic) from "what it looks like" (client) before writing a line of code**.
2. **Guard comments**: once a first working version exists, have kids add a short comment block at the top of their HTML/JS (or a short paragraph pasted into every follow-up prompt) naming the exact function names/endpoints that must not change. Backend concept taught: **the frontend-backend contract (which function names and data shapes cross the client/server boundary) is the thing that breaks when AI "helps," and naming it protects it** — this is the single most directly reusable trick for the "weak, forgetful AI" problem Ben flagged.

### Traps a kid will hit
- Manual copy-paste of a *whole file* both ways (Apps Script → Gemini Canvas → Apps Script) is exactly the workflow the class will actually use with plain gemini.google.com (no in-IDE integration for personal accounts) — and it's exactly the moment version loss happens if a kid forgets to save a copy before pasting Gemini's rewrite over their old file. Directly validates Ben's "save versions before big AI asks" instinct.
- Plaintext passwords in a Sheet (shown and explicitly flagged by the presenter) — a good teaching moment for "the AI will happily build the insecure-but-simple version unless told otherwise," but also genuinely fine for a classroom toy project as long as kids know it.
- The wizard's own Technical Stack step *locks* backend=Apps Script, database=Sheets — i.e., even this "no-code" tool assumes exactly our stack, reinforcing that the constraint is normal, not a limitation unique to a classroom.

### Doesn't transfer, and why
The "AI Architect & Designer" wizard tool itself is a third-party template the class won't use (too polished/opaque for teaching, and it embeds someone else's server-side Gemini-calling code that kids didn't write or understand) — treat it only as inspiration for the *prompting structure*, never as software to install.

## Honest caveats
This is a promotional video for the creator's own tool, so the three demoed apps are best-case, quickly-tested happy paths (a few clicks each, no attempt to break them). No actual "AI broke my working app and I had to fix it" moment is shown on screen — the guard-condition technique is presented as prevention, not as recovery from a real observed failure, so we can't verify from this video alone how well it holds up under repeated edits.

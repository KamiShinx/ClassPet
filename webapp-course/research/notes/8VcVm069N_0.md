# How to create an Apps Script Web API Endpoint for AJAX connections - output Sheet as JSON, doPost (Laurence Svekis, 22.3 min)

**What it is:** Hands-on tutorial (Whisper transcript, so no channel/date card beyond the title): build a standalone web-app endpoint that serves Sheet data as JSON via `doGet`, then a parallel `doPost` version, called from a separate local front-end (HTML+JS on VS Code Live Server) with `fetch`. Undated but stack (v8 runtime, `const`, modern editor) reads as recent-ish (2021-2023 era).
**Substance:** substantive - this is the closest thing in the batch to the class's actual target architecture (separate frontend calling an Apps Script JSON endpoint via `fetch`/POST).

## Ideas, in the video's order
- [0:00:00] Frames the whole lesson as: web app endpoint outputs JSON built from Sheet rows; a separate front-end fetches it. This is literally the shape of "hub" or "final project" architecture in CONTEXT.md.
- [0:01:24] Explicitly promises both GET and POST demonstrated against the same endpoint - useful side-by-side for teaching the difference.
- [0:02:21]-[0:03:51] Server code: `SpreadsheetApp.openById(id).getSheetByName('Sheet2')`, `getDataRange().getValues()`, loop with `forEach`, hand-build a plain object per row (`{first, last, fullName}`) since there are no headers. Good concrete example of "rows are just arrays, you must know the column order."
- [0:04:21] First-run permission dance shown live: running `doGet` in the editor triggers the OAuth consent screen. Worth flagging to kids as a real, unskippable step the first time any script touches Sheets.
- [0:05:20]-[0:05:49] `ContentService.createTextOutput(JSON.stringify(holder)).setMimeType(ContentService.MimeType.JSON)` - the canonical JSON-endpoint pattern, spelled out clearly with reasoning ("so a fetch knows it's getting JSON").
- [0:06:18] Deploy as web app, access "Anyone" - open endpoint, no auth. Direct trap: this is the exact permission trade-off the course needs to teach (open access = simple but insecure vs "only myself"/executes-as-you).
- [0:06:49]-[0:07:49] Front end is plain HTML/JS on VS Code + Live Server (separate origin, http, not Apps Script HtmlService) - i.e. this whole demo is basically the "hub" or Netlify-style separated-frontend pattern the class will need for the final project, months before webcam/CORS constraints even come up.
- [0:08:49]-[0:09:49] Classic fetch pattern: `fetch(url).then(res=>res.json()).then(data=>{...})`, logged to DevTools console - a clean minimal example to reuse almost verbatim for a first "call my endpoint" exercise.
- [0:09:49]-[0:11:22] Loop over returned array with `forEach`, build HTML via template literals and `innerHTML`. Notes explicitly that this is "front-end code" only - a good moment to draw the client/server line for students.
- [0:11:54]-[0:12:57] `doPost(e)`: introduces the `e.parameter` object and reads a `row` value from it to select one record server-side, instead of returning the whole sheet. Concrete demonstration of request parameters flowing server-side.
- [0:14:32] Redeploying doPost: must go to Manage Deployments -> Edit -> New Version to update the live `/exec` URL - **explicit statement that you cannot test doPost changes against the dev URL, only the deployed one**, so every doPost tweak requires a redeploy. This is a real, repeated trap a kid will hit and get confused/impatient about.
- [0:16:03]-[0:17:01] First attempt sends `JSON.stringify(myObject)` as the fetch body and it silently fails to parse server-side ("empty value") - shown as an actual live bug, not just told about. He debugges by logging the raw incoming body.
- [0:17:30]-[0:18:27] Fix: switch to `FormData` (`new FormData(); formData.append('row', 2)`) instead of a JSON string body - this fixes it. **Real, useful trap for kids: `doPost` reading `e.parameter` does not automatically parse a JSON body; FormData works "out of the box," raw JSON string does not (without extra parsing).** Worth flagging as outdated/fragile - 2026 practice would show parsing `e.postData.contents` with `JSON.parse` as the more standard modern alternative, but this video never does that.
- [0:18:56] Wires an `<input type="number">` to the POST body dynamically, i.e. an actual mini interactive UI, not just a fixed demo value - good small final step of the lesson.
- [0:20:22] Builds a `<ul>`/`<li>` list dynamically with `document.createElement`, appends to DOM - reusable minimal example for a "read one row, render it" exercise.

## For our class (14-15, Gemini writes the code, Apps Script + Sheets)
### Backend concepts it shows or explains
- Client vs server: an external HTML/JS page (not served by Apps Script) making `fetch` requests to a `.../exec` URL - directly the shape of "frontend hosted elsewhere talks to Apps Script backend" the class needs for the final project.
- GET vs POST distinction with the *same* backend function pattern, and how query params (`e.parameter`) differ from POST body handling.
- Endpoint permissions ("who has access") as an actual design decision with consequences, not just a checkbox to click through.
- Deployment versioning: dev URL vs the "New version" you must create to update the live doPost endpoint.

### Becomes something kids do (activity, mini-project, milestone), concrete enough to run next week
- "Class roster API": Sheet of names, `doGet` returns full list as JSON, a tiny external HTML page fetches and lists them. Then add `doPost` with a `row` or `id` parameter to fetch one entry - teaches read vs. filtered-read in one sitting. Concept taught: request parameters + JSON serialization.
- Extend to a button-driven "look someone up" UI with `<input type="number">` bound to the POST body - teaches the request/response loop end to end, testable in one 90-minute session.

### Traps a kid will hit
- Editing `doPost` code and testing it against the browser without redeploying a new version first - the dev URL genuinely does not reflect doPost changes for the deployed endpoint the way it does for `doGet`/HtmlService pages. Kids will think their fix didn't work.
- Sending `JSON.stringify(...)` as the fetch body and having `e.parameter` come back empty - a very plausible mistake since a "weak/forgetful" AI is equally likely to write `body: JSON.stringify(obj)` without also writing server-side `JSON.parse(e.postData.contents)`. Worth pre-empting with a project-memory note: "our POST bodies are FormData, not JSON, unless the .gs file explicitly parses `e.postData.contents`."
- "Anyone" access deploys an open, unauthenticated JSON endpoint to the whole internet - fine for a class exercise, but worth naming explicitly as insecure so kids don't assume it stays private.

### Doesn't transfer, and why
- The `FormData` workaround for POST bodies is a fragile pattern; 2026 practice (and most current AI-generated Apps Script code) would more commonly send `JSON.stringify` and parse `e.postData.contents` server side - flag this video's approach as a working-but-dated technique, not the modern default.
- VS Code + Live Server as the "external frontend" stand-in is fine for demonstrating the concept, but the class's actual final-project frontend will be Netlify-hosted, which raises CORS questions this video never touches (its Live Server is same-origin-ish and apparently had no CORS friction shown).

## Honest caveats
No CORS discussion at all despite calling a cross-origin endpoint from a local dev server - either GAS execution's default CORS headers happened to allow it, or Live Server's origin wasn't actually cross-origin in a way that mattered; either way, this is a gap the class must fill in themselves for the real Netlify case. The whoosh through the POST "doesn't work / switch to FormData" moment is authentic and valuable but is presented as "this is just how it's done" rather than explained as a JSON-vs-form-encoding issue - a kid copying this verbatim from Gemini would not understand *why* FormData was needed.

# Teachable Machine 3: Sound Classification (The Coding Train, 14.6 min)

**What it is:** Tutorial/demo, direct sequel to kwcillcWOg0. Dan Shiffman trains an audio model in Teachable Machine and swaps it into the same p5.js/ml5.js project, then iterates twice on what signal to control a Snake game with.
**Substance:** substantive: shows the audio-specific parts of TM in depth, plus two live experiments (ukulele notes, then spoken words) that double as an honest case study in what makes a classifier reliable.

## Ideas, in the video's order
- [0:00:34]-[0:01:07] Transfer learning again, but the base model this time is "Speech Commands 18w" (not MobileNet): pretrained to recognize 18 spoken English words (digits 0-9 plus up/down/left/right/go/stop/yes/no) plus "unknown" and "background noise" — TM strips those labels and retrains on your own sound classes the same way it did with images.
- [0:01:41]-[0:02:15] Every audio project needs a background-noise class first, recorded as one continuous 20-second clip, because the model needs a "nothing" example to compare real sounds against (echoes DFBbSTvtpy4).
- [0:02:15]-[0:02:50] The model's actual training unit is always 1 second of audio; TM's "Extract Sample" button chops any longer recording into 1-second pieces automatically.
- [0:05:10]-[0:05:42] Key concept explainer, worth reusing directly: the pictures you see during audio recording aren't photos, they're spectrograms — a visualization of which frequencies are loud at each moment — and that spectrogram image is literally what gets fed into the model, which is why an "audio classifier" is under the hood still an image classifier.
- [0:06:15]-[0:07:19] Code swap from the image version: `classifier = ml5.soundClassifier('<url>')`; no `createCapture(VIDEO)` needed, and critically no manual "classify again" loop — the sound classifier keeps listening continuously and calls your callback repeatedly on its own, unlike the image classifier's call-then-recall pattern.
- [0:07:58]-[0:08:30] Live miss: with only 3 trained sound classes + background noise, the model has no "person talking" category, so the presenter's own voice gets misclassified as whatever trained class it's statistically closest to — a direct lesson that an unlabeled real-world input doesn't get rejected, it gets forced into the nearest wrong bucket (same lesson as the image video's idle-frame behavior).
- [0:08:47]-[0:10:20] First experiment: trains 4 classes on individual ukulele chords (C, G7, F, A) to control a Snake game's directions. Works "kind of" — confidence scores aren't cleanly separated because the chords share overlapping frequencies/notes.
- [0:10:20]-[0:11:34] Switches to 4 individual open-string notes instead of chords, expecting more distinct spectrograms; modestly better but still not confidently separated in practice.
- [0:12:08]-[0:13:17] Second experiment: retrains on 4 spoken sounds instead (saying "up"/"down", plus a meow and a whistle), timed to fit the 1-second window — this works substantially better than either ukulele attempt, which the presenter attributes to the base model itself being trained on human speech, so novel non-verbal instrument sounds are working against the grain of the pretrained model.

## For our class (14-15, Gemini writes the code, Apps Script + Sheets)
### Backend concepts it shows or explains
A continuously-listening callback (no manual poll loop) is a different async shape than the image classifier's call-and-recallback pattern — worth contrasting directly with kwcillcWOg0 when teaching event-driven vs. request-driven code, since kids will meet both shapes again in `google.script.run` (request-response) vs. things like `onEdit` triggers (event-driven).

### Becomes something kids do (activity, mini-project, milestone), concrete enough to run next week
Not a good in-Apps-Script milestone (needs live mic, see below), but a strong live-demo-only lesson on model reliability: have kids try to control a game with two different sound choices (e.g. clapping patterns vs. spoken words) and predict/observe which works better, tying back to "the base model already knows human speech" — cheap, no coding required, teaches judgment about training data before they build anything.

### Traps a kid will hit
Assuming more/any training data guarantees a working classifier — the ukulele-chord failure is a clean counterexample to show before kids waste time training something doomed to be noisy. Also the "no unknown category" trap: if kids don't explicitly train a class for "nothing/off-target," ambient classroom noise or talking will get silently misclassified as one of their real classes rather than ignored.

### Doesn't transfer, and why
This is squarely a live-camera/mic feature per CONTEXT.md: `ml5.soundClassifier` requires a continuous `getUserMedia` microphone stream and nothing in this video (or the others in the batch) shows a way to run it against a pre-recorded/uploaded audio clip instead — TM's own model only exposes a live-mic listening mode in the library code shown here. That means sound classification is a Netlify-final-project feature, not something to attempt inside the Apps Script HtmlService sandbox during the year; flag this clearly since it's tempting to assume "just swap mic for upload" the way image classification can.

## Honest caveats
Same era as kwcillcWOg0 (Coding Train's original TM series), likely 2019 — architecture (transfer learning off Speech Commands 18w) is presented as current fact and is probably still accurate but wasn't independently re-verified here. The presenter's own experiments are explicitly inconclusive/anecdotal ("kind of works," "not as confident as I'd like") — reuse the finding ("speech-based signals outperform novel instrument sounds on this base model") as a hypothesis worth demonstrating, not a proven rule, and label it as his own live finding rather than documented TM behavior.

# Google Apps Script: Creating, Managing, and Automating Projects with Script (Laurence Svekis, 114.9 min)

**What it is:** a full "introductory Google AppScript course" — one long video stitched from many short lessons (title cards appear mid-video at [0:17:00], [0:39:15], [1:16:45] etc. marking lesson breaks). Live screen-recorded coding with a talking-head webcam overlay throughout. IDE described as "revamped in 2020," so this is 2020-era content, though the editor shown is close to the current one.

**Substance:** mixed. Roughly 45-55 of the 115 minutes is real API/concept teaching (Docs, Session, Gmail, Sheets writes, `doGet`, deployment, triggers, debugging). The other ~60 minutes is a slow, narrated tour of IDE chrome — menus, buttons, the command palette, sharing dialogs, project settings fields — clicked through one at a time with little conceptual payoff per minute. It is not silent live-typing, but it has the same low information density: long stretches of "here's another menu option" that a kid does not need and an AI-assisted class doesn't need explained at all (Gemini already knows where the Deploy button is).

## Ideas, in the video's order
- [0:04:23]-[0:08:49] Standalone scripts (independent files in Drive) vs. linked/bound scripts (live inside a Doc/Sheet/Slides via Tools > Script editor, get extra methods like `getActiveSheet()`/`getUi()`). Clear, reusable distinction.
- [0:18:17]-[0:19:55] First real code: `DocumentApp.create('name')`, then the OAuth consent flow shown in full ("Google hasn't verified this app" > Advanced > go to app). This exact wall recurs at [0:29:17], [0:37:06], [1:29:05] — a new consent prompt **every time a new Google service/scope is touched**, not just once per project.
- [0:22:45]-[0:27:40] `doc.getBody().appendParagraph()`, opening an existing doc by ID (`DocumentApp.openById`), appending text to an existing paragraph object. Straightforward object-model walk (app -> doc -> body -> paragraph).
- [0:28:45]-[0:30:21] `Session.getActiveUser().getEmail()` — introduces "who is currently running this script" as a concept, flags that Workspace admins can block it (generic aside, not relevant to personal Gmail accounts the class will use).
- [0:34:18]-[0:38:13] `GmailApp.sendEmail(email, subject, body)`, string concatenation to build the body from the doc's text + its URL. First full send-email example in the batch (simpler than the dedicated email videos in this batch).
- [0:39:21]-[0:48:00] IDE tour: rename project, sharing dialog (viewer/editor, "don't share the link with anyone" advice — generic but reasonable), Support menu, legacy-editor toggle. Mostly UI chrome, low teaching value.
- [0:50:55]-[0:59:44] Debugging: `Logger.log` vs `console.log` (both work now), setting breakpoints, stepping through a real bug (a variable that should increment but is being reset to a fixed value) — genuinely a good, concrete debugging demo, one of the strongest segments.
- [0:59:44]-[1:08:00] Autocomplete tour: hover docs, red-underline error hints, parameter suggestions. Some value (shows how to self-serve method signatures instead of guessing), but presented as a long UI tour.
- [1:08:00]-[1:16:42] Left-nav tour: Overview, Triggers panel, Executions log, Project Settings (GCP project number field — not relevant to this class). Triggers section explains time-driven triggers (run every N minutes/hours) and calendar-driven triggers, plus "always run the function once manually before attaching a trigger, or it may still ask for authorization" — a real, specific trap.
- [1:16:15]-[1:23:25] Libraries: creating a second script that wraps the YouTube Data API (`YouTube.Search.list`), explicit advice that **libraries are slower than native code and best avoided in real projects** — copy-paste separate `.gs` files instead. Useful mainly as "don't do this" guidance.
- [1:24:33]-[1:26:15] Deploying a script as a library (Deploy > New deployment > type "Library"), copying the deployment ID, adding it to a second project via Libraries > paste ID, versioning.
- [1:32:29]-[1:35:51] Writing API results into a Sheet: `sheet.appendRow()`, `JSON.parse(element)` to turn a returned JSON string back into a usable object, then pulling out nested fields (`obj.snippet.title`). This is the batch's only real "write structured data into a Sheet in a loop" example.
- [1:37:29]-[1:46:00] `doGet(e)` for web apps: two ways to return content — `ContentService.createTextOutput(str)` (plain text) and `HtmlService.createHtmlOutput(html)` / `.createHtmlOutputFromFile('index')` (rendered HTML/CSS/JS page). No JSON output and **no `doPost` anywhere in this video** despite the batch's theme naming it.
- [1:40:12]-[1:42:25] Deployment "execute as" (me vs. accessing user) and access-level options (only me / anyone with Google account / anyone), plus the dev-URL-vs-exec-URL distinction (dev always shows latest saved code but only to people with edit access; exec is frozen until you redeploy). Explained fast and thinner than in other Svekis videos on this topic — treat as a first pass, not the reference explanation.
- [1:46:25]-[1:55:00] Editor productivity tour: rename-symbol-everywhere, find/replace with regex, command palette, code folding, high-contrast theme. Generic editor tips, no backend content.

## For our class (14-15, Gemini writes the code, Apps Script + Sheets)
### Backend concepts it shows or explains
- Client vs. server split via the object model: script (server) reaches into Docs/Sheets/Gmail, nothing runs in a browser until `doGet` is used.
- A request's entry point (`doGet`) and the two ways a server can respond (plain text vs. rendered HTML) — thin but a valid first version of "what does a server do with a request."
- Deployment as a distinct, versioned step from saving code — the dev/exec split is a genuine backend concept (staging vs. production) even if explained quickly here.
- Triggers as server-side automation independent of any user click — a good contrast to the request/response model shown moments later.
- Writing structured results into a Sheet in a loop (`appendRow` + `JSON.parse`) as the API-response equivalent of a rudimentary "insert into database" step.

### Becomes something kids do (activity, mini-project, milestone), concrete enough to run next week
- Day-1 milestone: deploy a `doGet` that returns "Hello, \<your name\>" as plain text, then upgrade it to return a full HTML page — mirrors [1:37:29]-[1:46:00] almost exactly and gives every kid a real public URL in the first session.
- Debugging kata: hand kids a version of the broken for-loop from [0:55:18]-[0:58:00] (a variable reset instead of incremented) and have them find it with breakpoints rather than by reading the code — a concrete, reusable 20-minute exercise.
- "Log a list of things I like into a Sheet": adapt the `appendRow` loop at [1:32:29] to any small array of strings/objects the kids type in by hand (skip the YouTube API entirely) — teaches the write-loop concept without the library/API-key detour.

### Traps a kid will hit
- A brand-new consent screen appears every time a *new* Google service is touched, not just once per project — kids will think they "broke" something the second, third time it appears.
- `doGet` output is frozen at whatever the exec URL last deployed — editing code and refreshing the public URL shows nothing new until a new deployment is made. Flagged in the video but fast; needs its own explicit class explainer (S4 batch's videos cover this more thoroughly and should be the primary source).
- Trigger functions that were never run manually first can silently fail on "authorization required" the first time they fire on schedule — worth pre-empting: always click Run once before attaching any trigger.
- The video's own advice to avoid libraries for real projects is worth repeating to kids verbatim if Gemini ever suggests splitting a small class project across script-library projects — unnecessary complexity for this scale.

### Doesn't transfer, and why
- The entire library-deployment workflow ([1:16:15]-[1:37:00]) is explicitly called out by the video itself as something to avoid for real projects — skip teaching it to kids at all, beyond maybe mentioning "separate .gs files exist" for organizing code.
- The GCP-project-number / manifest-file settings tour ([1:14:30]-[1:16:09]) is enterprise/plugin-publishing territory, irrelevant to a personal-Gmail classroom project.
- No `doPost`, no JSON response from `doGet`, no CORS, no cross-origin fetch anywhere in this video — despite the batch label naming "JSON APIs, doGet/doPost." For the class's planned Netlify-frontend final project, this video alone is not sufficient; pair it with stronger JSON/`doPost` material from other batches (S4's `frejbw3eJTY`/`JOOUtlOKbak`/`AfA8twIVxRg` sequence covers this ground far better).

## Honest caveats
No AI-assisted building shown anywhere — this is 100% hand-typed instructor code, useful only as a reference for "what correct structure looks like," not as an example of how Gemini would build something or where it might go wrong. Nothing is technically outdated (Apps Script APIs shown are all current), but a genuinely large fraction of the runtime (menus, sharing dialogs, command palette, GCP settings) is IDE-tour filler with near-zero content-per-minute for a class where Gemini, not the student, will be driving the editor. Don't assign the full 115 minutes to students; if reused, cut to the ~10 short segments flagged above (roughly 45-50 minutes total).

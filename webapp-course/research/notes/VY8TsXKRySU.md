# Dots That Go for Walks: How to Maximize Minimal UI (GDC / Margaret Robertson, game director at Dots, 34.3 min)
**What it is / substance:** a GDC talk on minimalist UI design for mobile puzzle games (Two Dots, Dots & Co), built around a handful of concrete, nameable techniques (hide, merge, evacuate/kill) illustrated with real before/after screens from the speaker's own shipped games.
**No, not as homework whole** — 34 minutes, GDC-audience pacing (an extended Predator movie bit, lots of asides, one section literally about hard-currency IAP purchase-flow design). **With a guide**, though: unlike the other GDC talk in this batch, several of its techniques are genuinely simple enough for a 14-year-old to apply directly — see below.

## The ideas (in order, with [h:mm:ss])
- [0:02:13]-[0:03:16] Opening thesis (Paul Klee quote: "a line is a dot that went for a walk"): even the simplest shape can carry a lot if you push on what it can do — sets up minimalism as a discipline, not a limitation.
- [0:07:10]-[0:08:16] **Type is powerful but risky.** Big bold text can be a whole UI element by itself (shown identically solving onboarding for three different real games), BUT: [0:10:32]-[0:11:38] many games render type badly (Desktop Dungeons shown as a specific bad example — misaligned baselines, awkward outlines), and [0:11:38]-[0:12:44] "nobody reads" — if text has to compete with anything visually louder, players will ignore it. So if you use text as a core UI element, it has to dominate the screen, not compete with other detail.
- [0:12:44]-[0:13:51] **Making space is the real job.** Minimalist design isn't about having few elements, it's about giving the few elements you keep room to breathe — which means aggressively finding ways to remove or de-emphasize everything else.
- [0:13:51]-[0:17:13] **Technique 1: HIDE.** Don't show controls the player doesn't need right now. Example: Mini Metro tucks its speed controls behind a small clock icon in the corner — tap it, the controls drop down, tap again, they vanish — instead of a permanent row of buttons eating screen space.
- [0:17:46]-[0:20:59] **Technique 2: MERGE.** Instead of separate layers (an illustration + a button + a text label sitting next to each other), collapse them into ONE tappable object. Shown concretely: Dotson Co's currency-purchase screen went from a busy layout with separate illustration/button/info panels [0:18:22] to a version where each colored panel IS the button, illustration and all [0:19:12]-[0:19:26]. Touch Tone does the same: the "city" illustration itself IS the play button, no separate label needed.
- [0:20:59]-[0:22:22] **Technique 3: EVACUATE / KILL.** Cut features or decoration that aren't earning their place. Anecdote: a cloned/stolen version of their game added eyes to their turtle mascots — which made the designers realize their turtles never needed eyes at all, because "being a turtle" (moves on its own, hides in its shell when hit) already communicates everything a player needs, without a tooltip. Counter-example in the same beat [0:25:06]-[0:26:10]: a human character in another game (Reigns) DOES need eyes even without a nose, because eyes carry the sense of "this is a person I'm dealing with" that a turtle doesn't need — the lesson is to test each removal, not cut everything indiscriminately.
- [0:26:43]-[0:28:51] Another kill example: Dotson Co originally let you choose between two companion characters (rookie/expert) before each level, with lots of button-plus-illustration-plus-text UI to support the choice — they killed the two-choice feature entirely rather than keep trying to make its UI cleaner, because the choice itself was adding too much friction at a moment that needed to feel fast.
- [0:29:22]-[0:31:34] **Color-blind-safe design as forcing function.** Every mechanic in their games must work with color-blind mode ON (shapes/patterns substitute for color-only meaning) before it ships — described as "prodigiously worthwhile" because designing for that constraint up front frees them to use color more boldly everywhere else, since they already know the game doesn't *depend* on color alone.
- [0:31:34]-[0:33:14] **"Invisible ink": sound and vibration substitute for visual clutter.** Example: a satisfying buzz/vibration when you complete a square means they don't have to add extra visual flourish to communicate the same success — a non-visual channel does the job instead.

## Vocabulary for prompting Gemini
- **Hide (progressive disclosure)** → keep secondary controls tucked away until tapped, instead of always-visible → "put the settings/speed controls behind a small icon in the corner that expands when tapped, not as permanent buttons."
- **Merge** → combine an illustration, its label, and its button into a single tappable element → "make the whole card tappable and remove the separate 'Play' button under the image."
- **Evacuate / cull** → remove a feature or decoration that isn't pulling its weight → "do we actually need this? does removing it lose anything the player needs?"
- **Color-blind-safe** → a design that still works if color can't be distinguished (uses shape/pattern too) → "make sure the red/green success and failure states are also distinguishable by icon or shape, not color alone."
- **Non-visual feedback** → sound or (on mobile) vibration used instead of an extra visual effect → "add a short sound effect when a move succeeds instead of adding another animation."

## Page material
- **Rules of thumb:**
  1. Don't show a control until the player needs it — hide it behind a small icon and reveal it on tap.
  2. If an illustration, a label, and a button always appear together, make them ONE tappable thing instead of three separate elements.
  3. Before adding decoration (an icon, extra text, an animation), ask if the thing it's attached to already communicates what's needed without it.
  4. If you use big text as a UI element, make it the biggest/boldest thing on the screen — competing with other visual noise means players won't read it at all.
  5. Test your color choices as if you were color-blind (or use a a browser color-blindness simulator) — if meaning depends only on red vs green, that's a bug, not just an accessibility nice-to-have.
- **Exercises:**
  1. Find one screen in your app with 3+ separate visual pieces (icon + label + button) describing the same thing, and try merging them into a single tappable card.
  2. Find one control in your app that's always on screen but rarely used, and hide it behind an icon that reveals it on tap.
  3. Look at your game's colors with a color-blindness filter (many phones/browsers have one built in) — does anything become impossible to tell apart?
- **Quiz:**
  1. Q: What's the "merge" technique? A: Combining separate visual pieces (illustration, label, button) that always go together into a single tappable UI element, instead of keeping them as three things sitting near each other.
  2. Q: Why does designing for color-blind players first make it EASIER to use bold colors elsewhere, according to the talk? A: Because once you know the game's meaning never depends on color alone, you're free to use color for richness/mood without worrying it'll break understanding.
- **For a game built with Gemini on Apps Script (turn-based/idle, no real-time):** hide, merge, and evacuate/kill all apply directly and cheaply — e.g. hide an idle game's "settings" or "stats" behind a small gear icon instead of a permanent panel; merge an item's icon + name + "buy" button into one clickable row instead of three separate HTML elements; before asking Gemini to add a new decorative flourish, ask whether the underlying element already communicates the idea. Color-blind-safe design is easy to ask Gemini for directly ("also show a small icon or pattern, not just a color change, for success/failure states"). What doesn't fit: haptic vibration feedback (not available to a browser HtmlService page in any reliable cross-device way) and the whole hard-currency purchase-flow example (there's no in-app purchasing in a school project) — mention sound effects as the realistic substitute for both.

## Caveats
This is one of the two GDC talks the brief flags as professional-level, and it shows: it assumes a live commercial mobile game with a dedicated design team iterating for months on a single purchase screen, and roughly the first 5 minutes and several later asides (an extended Arnold Schwarzenegger/Predator bit, a joke about buying a vinyl record) are stage patter that add nothing extractable — skip them and point kids at specific timestamps instead of the full 34 minutes. All examples are mobile touchscreen puzzle games (Two Dots, Mini Metro, Reigns, Touch Tone) — translate "tap" to "click" for a browser-based Apps Script app, and note that unlike the other GDC talk in this batch (ONYmBBZiBj8), this one's core techniques (hide/merge/cut) are genuinely simple enough to hand to a 14-year-old nearly as-is, just trimmed for length.

# Batch S6 summary - Laurence Svekis Apps Script channel

7 videos. **Split sharply in relevance**: 3 videos (8VcVm069N_0, EiF_dpWKLNE, q9QkAfOX44s) are genuine web-app/doGet/doPost/deployment material and are the strongest content in this batch for the class. The other 4 (dxKo96UNkXc, 7KkPv5trdVw, YMdRSw2iMXI, lQDcc_VITsk) have **no web app, no doGet/doPost, no deployment, no frontend at all** - they're bound-script UI menus, custom Sheets formulas, and Docs/email automation. Flagging plainly per the brief: those four are only tangentially useful (Sheets/JS fluency, defensive-coding habits, one debugging story) and shouldn't be treated as web-app curriculum.

## Concept explainers worth reusing
- **Dev URL vs deployed/executable URL** [q9QkAfOX44s 0:07:49-0:10:34]: the clearest treatment in the batch. Live demo of editing code, seeing the dev URL update immediately but the deployed `/exec` URL stay frozen until a new version is pushed. This is probably the single most important Apps-Script-specific trap for the whole course and this is the best raw explanation of it to build a class demo around.
- **Framed vs raw output** [EiF_dpWKLNE 0:08:19-0:09:24]: `ContentService` output is unframed (URL and content style differ) vs `HtmlService` output stays framed in the `/exec` iframe. Good vocabulary for explaining why JSON endpoints "feel" different from HTML pages.
- **`e.parameter` vs `e.parameters`, GET query strings** [q9QkAfOX44s 0:10:34-0:13:17]: side-by-side demo of a duplicate query key showing single-value vs array behavior. Worth reusing directly - subtle enough that kids (and Gemini) will get it wrong without seeing it demonstrated.
- **JSON endpoint pattern** [8VcVm069N_0 0:05:20-0:05:49, EiF_dpWKLNE 0:05:31-0:07:45]: `ContentService.createTextOutput(JSON.stringify(x)).setMimeType(ContentService.MimeType.JSON)` shown twice, consistently - safe to treat as the canonical idiom to teach.
- **Server->client data handoff via scriptlets** [EiF_dpWKLNE 0:15:22-0:21:56], including a live `ReferenceError` when a variable isn't attached to the template's output object - a good "nothing crosses the boundary unless you explicitly send it" demo, though the PHP analogy used to introduce scriptlet syntax won't land for this audience and needs replacing.

## Project seeds
1. **Row picker via query string** (from q9QkAfOX44s) - deploy a doGet that reads `?id=` from the URL and renders one Sheet row as HTML. No JS frontend needed. Teaches: request parameters, dev-vs-deployed URL, Sheet reads. Good first web-app milestone, one session.
2. **Class roster JSON API + fetch page** (from 8VcVm069N_0) - `doGet` returns all Sheet rows as JSON; a separate HTML/JS page (can be the literal shape of the eventual Netlify frontend) fetches and renders the list. Teaches: JSON serialization, fetch/promises, client vs server split. This is the closest thing in the batch to the actual final-project architecture (separate frontend calling an Apps Script `/exec` endpoint).
3. **"Look someone up" with doPost** (from 8VcVm069N_0) - extend #2 with an `<input>` bound to a POST body (as FormData, not JSON.stringify - see trap below) and a `doPost` that filters one row. Teaches: POST vs GET, request bodies, redeploy-to-update-doPost trap.
4. **Live Sheet-backed page via scriptlet template** (from EiF_dpWKLNE) - an HtmlService template that loops Sheet rows server-side and renders a list, refreshed on reload. Teaches: templated server-side rendering, live data binding, without needing fetch/JS at all - a simpler alternative on-ramp to #2 for a weaker group.
5. **Custom menu + find & highlight** (from dxKo96UNkXc) - bound-script warm-up, not a web app: teaches ranges, `onOpen`, loops, before web apps are introduced. Good pre-web-app Sheets-fluency exercise.
6. **"Generate and email me a certificate" bonus feature** (from YMdRSw2iMXI / lQDcc_VITsk) - a non-web add-on for an existing Sheet-backed project: build a PDF or Doc from row data and email it. Teaches: blobs/MIME conversion or DocumentApp, plus the off-by-one row-index pattern. Optional flourish, not core.

## Traps
- **Redeploy required for doPost/doGet changes to reach the live URL** [q9QkAfOX44s, 8VcVm069N_0] - the single biggest recurring trap across this whole batch; every kid and every AI edit to server code will hit "I fixed it but it's still broken" until they learn to redeploy a new version. Worth a standing class rule/checklist item.
- **POST body format mismatch**: `JSON.stringify(obj)` sent as the fetch body leaves `e.parameter` empty; switching to `FormData` fixes it in this batch's examples [8VcVm069N_0 0:16:03-0:18:27], but the more robust 2026 fix (parsing `e.postData.contents` with `JSON.parse` server-side) is never shown anywhere in this batch - flag as a gap to fill from elsewhere, since a weak AI is just as likely to write the broken `JSON.stringify` version as the working `FormData` one, without knowing why either works.
- **Silent type coercion in Sheets** (numbers becoming Date objects) [dxKo96UNkXc 0:22:44-0:24:24] - real, invisible-until-inspected bug; needs `Format > Plain Text` and defensive code. A strong entry for the "Sheets speed/quirks" trap category the brief asks about.
- **Off-by-one row indexing** (`index+2` for header row + zero-based index) appears in both YMdRSw2iMXI and lQDcc_VITsk - common enough across the channel to teach once, generally, rather than per-project.
- **No error handling in loops that send email/create files** - none of the automation videos in this batch wrap `MailApp.sendEmail` or `DocumentApp.create` in try/catch; a bad row (invalid email, duplicate name) would likely abort the whole loop silently. Directly relevant to the "AI breaks working projects" framing - worth a standing habit: wrap side-effecting loop bodies in try/catch and log failures per-row.
- **Forgetting `.evaluate()` after `createTemplate()`** [EiF_dpWKLNE 0:12:07-0:12:39] - produces an unhelpful "unsupported output type" error; worth a one-line mention if scriptlet templates are taught.
- **Bound vs standalone confusion**: q9QkAfOX44s explicitly recommends standalone scripts for web apps as best practice; dxKo96UNkXc requires a bound script for `getUi()`/`onOpen`. Worth a clear rule of thumb for kids: "web app -> standalone; menu/trigger inside a specific Sheet -> bound."

## Where videos agree or contradict
All three web-app videos independently reinforce the same core Sheet-read idiom (`openById`/`getActiveSpreadsheet` -> `getSheetByName` -> `getDataRange().getValues()` -> loop) and the same deployment dialog (execute-as / who-has-access), which is reassuring consistency to build a class script around. No real contradictions found. One soft tension: q9QkAfOX44s recommends standalone scripts as best practice for web apps, while three of the four non-web-app videos all use bound scripts by necessity (menus, custom functions, or simply "the script tied to this Sheet") - not a contradiction so much as different tools for different jobs, worth stating explicitly to avoid kids thinking one approach is always wrong.

## What to cut
- Cut lQDcc_VITsk and YMdRSw2iMXI from any "web app" teaching sequence entirely - they are Docs/Drive/email automation with no HTTP request-handling content whatsoever. Keep only as optional "bonus feature" references if a specific kid project wants to generate/email a document.
- Cut 7KkPv5trdVw's custom-functions material from the API/backend track - it's Sheets-formula scripting, not request/response programming. Its `try/catch` + Maps geocoder example is the one salvageable piece, useful only as a defensive-coding reference.
- Cut dxKo96UNkXc's extended counter/prefix debugging sequence from anything kids build directly (too fiddly for a first project) but keep it narrated as an example of "the fix didn't work the first two times either" - genuinely useful raw material for normalizing iterative debugging with a weak AI.
- The PHP-analogy framing of scriptlets in EiF_dpWKLNE should be dropped or replaced if that section is reused - won't land for 14-year-olds.

## Anything usable for the hub
The JSON-endpoint pattern from 8VcVm069N_0 and the framed/unframed distinction from EiF_dpWKLNE are both directly reusable for the hub itself (e.g., an admin `doGet` returning course data as JSON to a separately-hosted hub frontend). The dev-URL-vs-deployed-URL discipline from q9QkAfOX44s should become a standing operating habit for building the hub, since Ben will be iterating on it constantly.

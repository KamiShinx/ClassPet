# How to Design Figma-Quality UI with AI (Detailed Prompts, Skills & Gemini 3.1 Pro) (Made by Sourasith, 18.5 min)
**What it is / substance:** A hands-on walkthrough of a real design workflow inside "Aura Build" (a paid, Lovable/Bolt-style AI app builder with a Gemini/GPT/Claude model picker), showing basic vs. detailed vs. structured prompts, a 6-part prompt formula, reusable "skill" style-guides, and section-by-section/component-by-component iteration. **Is it homework-worthy:** Yes, with a guide — the prompting vocabulary and workflow discipline are genuinely useful and well demonstrated, but it all happens inside a tool the kids don't have, uses a multi-model picker they don't have, and references paid-credit limits that don't map 1:1 to Gemini's rate limits, so a teacher needs to translate "type this into Aura Build" into "type this into Gemini web chat, then paste the HTML/CSS into your Apps Script file."

## The ideas (in order, with [h:mm:ss])
- [0:00:00] AI can generate a full UI (landing pages, dashboards, animations) from a text instruction.
- [0:00:08] Generic-looking AI-made UI is usually not the AI's fault — it's caused by instructions that aren't clear or detailed enough.
- [0:02:14] A **basic prompt** is short and vague (example given: "create a SaaS landing page for a sales analytics platform"). It produces something usable but generic — not "wow."
- [0:02:47] You can steer even a basic prompt with a **reference**: a screenshot of a section from another site, or the actual code of a reusable component you already have, so new elements match that style.
- [0:03:56] A reference image guides the AI visually — in the demo it copied a green glow effect from the reference image — but without any reference or detail, the result stays visually basic.
- [0:04:30] Rule stated three times for emphasis: never stop at one prompt. Spend more time refining each section, then each component.
- [0:05:02] Treat a reference screenshot like a **wireframe**, not a source to copy: it should guide layout/structure, and you should adapt it to your own style — because you can't use basic shape tools (rectangle, circle) the way you would in Figma, so images stand in for that.
- [0:05:35] A **detailed prompt** adds specifics (layout structure, container width, color palette, UI components, product visuals) and produces one strong, specific result — but you need a new detailed prompt to get a different result; it doesn't give you variety on its own.
- [0:06:10] The **6-part structured-prompt formula**: (1) describe the product — what it is and does; (2) give a design direction — mode, mood, accent color; (3) layout structure — the page's section order, its "skeleton"; (4) visual system — the look-and-feel language (shapes, shadows, spacing, color rules), separate from structure; (5) components — the exact UI pieces to include; (6) technical instructions — framework, responsiveness, code cleanliness.
- [0:08:27] If you don't know how to write a detailed prompt yourself, describe your idea loosely and ask the AI to turn it into a detailed prompt that includes design direction, layout structure, visual system, components, and technical instructions.
- [0:08:58] A **skill** (jargon: in this tool, a saved reusable instruction preset) differs from a one-off prompt — it locks in a role/expertise/style so you don't retype the same detailed instructions every project. The presenter admits he personally writes a fresh detailed prompt each project instead of reusing skills, because every project differs.
- [0:10:08]–[0:11:48] Advice for writing your own skill/style-guide: don't just say what to build, say **how to think** ("act as a senior product designer"); include a system overview, visual direction, layout rules, component rules, interaction rules (motion/behavior), and a list of what to avoid.
- [0:10:42] Workflow discipline: always start with the hero/top section first; never try to one-shot the whole page in a single prompt — it costs more prompts to go section by section, but a single big prompt gives something generic that "anyone can do."
- [0:11:15] AI builders don't automatically apply standard web/mobile design conventions the way a human following Figma guidelines would — you must restate the design system and style every time, though adding a responsive-design rule set helps keep results usable across screen sizes.
- [0:12:23] After a section looks clean, don't stop: adjust the font, fix colors you don't like, refine spacing — then move to polishing components like a dashboard chart.
- [0:12:56] Add animation/motion detail in the **same** prompt as a component's visual refinement (rather than styling now, animating later) — this saves a prompt/credit and keeps the two connected.
- [0:13:31] For small fixes, you can edit the generated code by hand instead of spending another prompt, if you're comfortable reading code.
- [0:14:05] With direct access to a chat AI app (ChatGPT/Gemini/Claude, separate from the builder), you can paste generated code there and ask it to fix/improve it — useful because the AI builder itself has a prompt/credit limit before you must pay for more.
- [0:14:39] Reuse your own previously generated components (e.g. a donut chart built earlier in the project) instead of re-prompting from scratch, and copy/paste style properties between elements the way you would in Figma, to avoid wasting prompts.
- [0:15:50] Duplicate a section and prompt only the duplicate, instead of re-generating/re-checking the whole page's code — faster, and avoids the AI touching unrelated code.
- [0:16:59] Once layout is solid, add global "on load" and "on scroll" animations — you can prompt for the animation code or hand-write it (the video shows CSS keyframes placed in the page head, applied via Tailwind classes on elements).
- [0:17:35] For multi-page sites: use the builder's page feature, define how transitions between pages should work, generate the new page with another detailed prompt, then link navigation text/buttons to it.

## Vocabulary for prompting Gemini
This is the core of the video — concrete, reusable prompt phrasing:

- **Basic prompt** → a short, vague instruction → *"Create a SaaS landing page for a sales analytics platform."* Gets you something generic, fast.
- **Detailed prompt** → adds specifics so you get one strong, specific result → *"Design a dashboard with a centered container, dark navy background, and a thin green line chart."*
- **Reference image as wireframe** → attach/describe a screenshot and say what to copy vs. change → *"Use the layout of this screenshot as a structure reference for the hero section, but use my own colors and fonts — don't copy the design exactly."*
- **Reusable component reference** → paste existing code so new pieces match it → *"Here is the code for my existing button. Make the new card use the same border-radius and color style."*
- **Product description** (formula part 1) → what the app is/does, one or two sentences → *"This is a to-do list app for students to track homework by subject."*
- **Design direction** (formula part 2) → mode + mood + accent color → *"Light mode, neutral off-white background, one green accent color. Feels calm and premium, not playful."*
- **Layout structure / "skeleton"** (formula part 3) → top-to-bottom section order → *"Centered container. Order: navbar, hero with big title, 3 feature cards in a row, a dashboard preview, pricing table, footer."*
- **Visual system** (formula part 4) → look-and-feel rules independent of layout → *"Rounded corners (12px), minimal shadows, generous white space, neutral gray background with the accent color used only on buttons."*
- **Components** (formula part 5) → name the exact UI pieces → *"Include a metric card, a line-chart card, and a table with 5 rows."*
- **Technical instructions** (formula part 6) → tech/code constraints → *"Use plain CSS, make it responsive down to phone width, keep the HTML structure clean."*
- **Meta-prompt (ask AI to write your prompt)** → describe your idea loosely, then: *"Turn this into a detailed prompt that includes design direction, layout structure, visual system, components, and technical instructions."* — directly reusable in Gemini, word for word.
- **Skill / saved style guide** → (tool-specific feature name; the underlying idea transfers) a long reusable instruction block written once and pasted at the start of every new chat about that project, since Gemini forgets between chats.
- **"Act as [role]" framing** → sets the AI's stance instead of just describing output → *"Act as a senior product designer designing a premium SaaS dashboard."*
- **Constraints / avoid-list** → say what NOT to do → *"Avoid a generic startup SaaS look, avoid playful illustrations, avoid colorful gradients, avoid overly minimal layouts."*
- **Section-by-section prompting** → ask for one section only → *"Design only the hero section for now. Don't build the rest of the page yet."*
- **Component-level follow-up edit** → change just one already-built piece → *"In the dashboard card, change the chart to a thin line chart with a soft glow under the line, and reduce the label font size slightly."*
- **Combine visual + motion in one prompt** → *"Style this card with a soft shadow on hover, and animate the number counting up from 0 when the page loads."*
- **Duplicate-then-edit** → *"Duplicate the last feature card. In the new copy only, change the icon to a shield and the text to describe security scanning."*
- **Exact spec tokens (hex/px)** for reproducibility → *"Background #0F172A, border radius 12–14px, border white at 10% opacity."*
- **Font-pairing instruction** → *"Use Inter for body text and Space Mono for small labels."*

## Page material
- 3-6 "rules of thumb" for the library page.
  1. Write your prompt in parts, in this order: what it is → how it should feel → what order the sections go in → what it should look like (colors/shapes/spacing) → which components to include → any tech rules.
  2. One vague prompt gives one generic result. Plan to prompt each section, then each component inside it, separately — never the whole page at once.
  3. A reference screenshot tells the AI your layout, not your final look — say what to keep (structure) and what to change (colors/style) explicitly.
  4. Say what to avoid, not just what to include ("avoid gradients, avoid playful illustrations") — negative instructions cut down on generic AI defaults.
  5. Keep your full style instructions (product description + design direction + layout + visual system) saved in one note, and paste that whole block into every new Gemini chat about the same project — Gemini has no memory between chats.
  6. When a result mostly works, change ONE part at a time (a color, a chart, one card) instead of regenerating everything — faster, and less likely to "nuke" what already works.
- 1-3 short exercises a kid can do at home with their own app or game.
  1. Take your current Apps Script app's UI (or a page you like elsewhere) and describe it back using the 6 categories (product, direction, layout, visual system, components, technical) as if about to prompt it from scratch — see what's missing.
  2. Screenshot your own app and write two short lists: "keep the structure of this" and "change the style of this" — practicing the reference-not-copy distinction from [0:05:02].
  3. Pick one button, card, or panel and write a component-only refinement prompt (change just that piece) instead of a whole-page prompt; compare how much of the rest of the page changed by accident vs. stayed untouched.
- 1-2 quiz questions with answers.
  1. Q: What's the difference between a basic and a detailed prompt in this video? A: a basic prompt is short/vague and gives one generic result; a detailed prompt adds specifics (layout, colors, components) and gives one specific, stronger result — but a different result needs a new detailed prompt.
  2. Q: Name the six parts of the structured-prompt formula from [0:06:10]. A: product description, design direction, layout structure, visual system, components, technical instructions.
- How this applies to an Apps Script web app's UI (forms, dashboards, cards) built by describing it to Gemini: the 6-part formula maps directly. Product description = what the tool/app does. Design direction = light/dark mode, one accent color, mood. Layout structure = the order of a form's fields or a dashboard's cards, top to bottom. Visual system = corner roundness, spacing, shadow use, one color rule — plain CSS pasted into an Apps Script HTML file handles this fine. Components = name the exact Apps Script UI pieces ("a form with 4 fields, a submit button, a results table reading from a Sheet"). Technical instructions = "use plain CSS, no external libraries, responsive down to phone width" — note that the video's Google-Fonts pairings may need to become "use system fonts only" if a Ministry network blocks external font loading; untested, flag it. Section-by-section and component-only prompting matter *more* for Apps Script kids than for the video's presenter, because a whole-page regenerate is exactly the scenario where the weak, forgetful AI can "nuke" a working app — always request one form/one card at a time and re-paste only that snippet back into the .gs/.html files.

## Caveats
- The tool used throughout is **Aura Build**, a paid multi-model AI website builder (comparable to Lovable/Bolt/Visual per the presenter's own comparison at [0:01:05]) — not Gemini web chat. It provides a model picker (Gemini/GPT/Claude/image models), a reusable "skills" library with a UI for attaching them, per-component "select and edit" side panels, a page-management system for multi-page sites, and Figma-style copy/paste of properties. Kids have none of this — only a Gemini web chat window and the Apps Script editor.
- "Skills" as a saved, click-to-attach preset with its own marketplace ([0:08:48]–[0:11:12]) don't exist in Gemini's free web chat. The workaround that DOES transfer: keep the skill's full text in your own notes and paste the whole block manually into a new chat each time — more typing, same effect, and this is explicitly necessary for kids since Gemini forgets everything between chats.
- The reference-image workflow (screenshot → attach to prompt) may or may not work the same way in the kids' Gemini web chat depending on whether their Ministry account/version supports image attachments — check this before assigning it as a technique to rely on.
- The video's font pairings (Inter, Space Mono, Manrope, IBM Plex Mono, Plus Jakarta Sans, DM Mono) are Google Fonts loaded by the builder; using them in Apps Script HtmlService requires linking Google Fonts by URL, which may or may not be allowed by Ministry network policy — flag as untested rather than assuming it works.
- The presenter explicitly says a full landing page can take "5, 30 minutes, or more" of section-by-section polishing and deliberately doesn't show the whole process on screen — the video teaches vocabulary and workflow discipline, not a fast recipe; doing this properly needs real class time, not a rushed homework slot.
- The presenter's comments about spending "credit" and needing to "buy more prompts" ([0:10:42], [0:14:05]) describe Aura Build's paid quota system, not Gemini's rate limits directly — but the underlying lesson (plan and batch your prompts because each one is a scarce, rate-limited resource) transfers directly to Gemini web chat's own limits.
- This video is about SaaS/dashboard/landing-page design, not game UI — it is the closest genre match to Apps Script's forms/dashboards use case, and has essentially nothing that maps to a turn-based/idle browser game specifically (no game-state, scoring, or interaction-loop discussion anywhere in the transcript).
- The on-camera host segments ([0:00:48]–[0:01:20], [0:18:16]–end) are short talking-head cutaways with no additional technical content beyond what's in the transcript — safe to skip if only extracting technique.

# Accessibility Fundamentals with Rob Dodson (SFHTML5 conference talk, 28.2 min)
**What it is / substance:** a conceptual deep-dive into HOW a browser actually talks to a screen reader (the "accessibility tree"), why native HTML elements are the easy path, and how/when to reach for ARIA — including a live-coded example turning a plain `<div>` into a real checkbox.
**With a guide** — the core idea (10-15 min of it) is excellent and genuinely explains "what's under the hood," but at 28 minutes with a slow, talk-paced delivery it's too long to assign whole; pull specific segments.

## The ideas (in order, with [h:mm:ss])
- [0:02:44]-[0:04:24] **Affordance** = something about an object's design that tells you how to use it without an instructions manual (a teapot's handle says "pick me up here," its spout says "liquid comes out here"). Visual design fakes affordances for sighted users (a button *looks* clickable) — the whole talk is about how to give the SAME information to someone who can't see the screen.
- [0:05:31]-[0:07:10] **The pipeline**: your HTML gets parsed into the DOM (the browser's live model of your page); the browser ALSO builds a second, separate tree called the **accessibility tree**, which prunes out purely-visual stuff (layout `<div>`s) and keeps only what's semantically meaningful (buttons, text, form fields). A screen reader only ever sees this second tree, not your raw HTML.
- [0:08:19]-[0:09:57] Each node in that tree has properties: **role** (what kind of control it is, e.g. "combobox"), **name** (its label), **state** (e.g. checked/unchecked, collapsed/expanded), and sometimes **value**. Chrome's DevTools (since Chrome 64) has an Accessibility panel that shows you this live, next to the regular Elements/CSS panels — genuinely useful for debugging "why isn't my screen reader saying what I expect."
- [0:10:33]-[0:14:23] **Use the right native HTML element and you get all this for free** — a real `<button>` already announces "button" with no extra work. Style a `<div>` to *look* like a button and a screen reader just says "group" — nothing tells the user it's clickable. His rule of thumb: "don't make your life hard — use the right element for the job."
- [0:14:56]-[0:16:56] **ARIA** (Accessible Rich Internet Applications) exists for the cases with no native element (custom tabs, a carousel, a tree widget). Critical point, repeated on-screen for emphasis: **ARIA changes only what gets ANNOUNCED — it adds zero behavior.** Adding `role="checkbox"` does not give you spacebar-to-toggle for free; you still have to write that JavaScript yourself.
- [0:17:08]-[0:19:23] To actually learn ARIA, don't read the raw W3C spec (he shows it and calls it a bad way to learn) — use the **ARIA Authoring Practices Guide (APG)**, which lists common UI patterns (checkbox, tabs, dialog, combobox...) with exactly which roles/states/keyboard behavior each one needs.
- [0:19:56]-[0:26:32] **Live demo**: he builds a fake checkbox out of a styled `<div>` with click + keyboard support already working visually — but a screen reader just says "group." He fixes it step by step with DevTools live: adds `role="checkbox"`, then `aria-checked="true"`, watches the accessibility tree update in real time, tests with VoiceOver each time. Then adds a label two ways — `aria-label` (a plain text alternative, good for icon-only buttons like a hamburger menu) and `aria-labelledby` (points at another element's text, or even multiple elements, to build up a label — e.g. "men's outerwear" + "shop now" = "men's outerwear shop now button").

## Vocabulary for prompting Gemini
- **Accessibility tree** → the browser's second, screen-reader-facing model of the page, separate from the DOM → mostly background knowledge, not a phrase kids will prompt with, but useful for understanding *why* semantics matter.
- **Role** → what kind of control something is (button, checkbox, combobox) → "make sure the custom dropdown has role='combobox', not just a styled div."
- **Native/implicit semantics** → the free role+behavior you get from using the real HTML tag → "use a real `<button>` element instead of a `<div onclick>` so it's accessible for free."
- **ARIA** → a set of HTML attributes that only change what gets announced to assistive tech, never behavior → "since this is a div-based custom widget, add ARIA roles and states."
- **aria-label / aria-labelledby** → a text label for an element, either written inline or pointing at another element's text → "give the hamburger menu button an aria-label of 'Main menu' since it has no visible text."
- **aria-checked / state** → a true/false (or other) property announced alongside the role → "toggle aria-checked when the custom checkbox is clicked."

## Page material
- **Rules of thumb:**
  1. Always ask Gemini for the real HTML element (`<button>`, `<input>`, `<select>`) before accepting a styled `<div>` that merely *looks* like one.
  2. Remember ARIA only changes what's *announced* — if you add `role="checkbox"` to a div, you still have to write the click/keyboard code yourself.
  3. If you must build a custom control, look up its pattern in the ARIA Authoring Practices Guide rather than guessing attributes.
  4. Give icon-only buttons (like a hamburger menu with no text) an `aria-label` so screen reader users know what they do.
  5. A page has two trees: what you wrote (DOM) and what gets announced (accessibility tree) — they're not automatically the same thing.
- **Exercises:**
  1. Open Chrome DevTools on your own app, click an important button, and check the Accessibility panel — does its "Name" say something useful, or is it blank/wrong?
  2. Find one clickable thing in your app that is a `<div>` instead of a real `<button>`. Ask Gemini to change it to a real button and check nothing else broke.
  3. Pick one icon-only control in your app (if you have any) and add an `aria-label` describing what it does.
- **Quiz:**
  1. Q: If you add `role="checkbox"` and `aria-checked="true"` to a `<div>`, does clicking it now toggle automatically? A: No — ARIA only changes what's announced, not behavior; you still need the click/keyboard JavaScript yourself.
  2. Q: What's the fastest way to make a clickable `<div>` accessible for free, without any ARIA at all? A: Use a real `<button>` element instead — it comes with the right role and keyboard behavior built in.
- **For a game built with Gemini on Apps Script:** directly usable — when asking Gemini for HUD buttons, inventory tiles, or menu toggles, specify "use real `<button>` elements" rather than accepting styled divs, since Gemini (like any LLM) will happily generate div-based fake buttons if not told otherwise. For anything genuinely custom (a drag-styled inventory slot, a custom dropdown for choosing a difficulty), this is where `role`/`aria-*` attributes belong. Doesn't fit: most of a turn-based/idle browser game's UI can just use native elements, so ARIA will rarely be needed — flag this as "good news, you probably won't need most of this talk."

## Caveats
This is a 2017-2018-era conference talk (references Chrome 64, shows an older DevTools UI): the Accessibility panel's exact layout has changed since, and some browsers now expose more of this tooling directly in the Elements panel without needing to dig — but the concept (DOM -> separate accessibility tree -> ARIA fills semantic gaps only) is unchanged and still exactly how it works. Talk-length pacing (lots of "so," "right," repeated slide text held for 30+ seconds while he talks) means the 28-minute runtime holds maybe 12-15 minutes of unique content — plan to point kids at specific ranges, not the whole thing. No mention of mobile/touch accessibility or Apps Script/Google Sheets contexts at all — purely general web.
